# Decision log

A running list of the important choices in this build, the alternatives
considered, and why each was picked. This matters more than polish.

- **Transparent points score, not a machine-learning model.**
  Considered: a logistic regression / gradient boosting on the CSV.
  Rejected for the shipped engine: the brief requires every decision to
  carry a plain-English reason and thresholds a non-technical person can
  change. A points system gives both for free; a model would need a
  separate explanation layer and retraining to change a threshold. The
  score still ranks risk correctly (September bucket RTO rates rise
  21.7% → 32.4% → 70% → 100%).

- **Geography at state level, never pincode level.**
  Considered: Operations' suggestion to stop COD in bad-history
  pincodes. Rejected after checking the data: 1,067 distinct pincodes
  for 2,017 resolved orders, no pincode with more than 12 orders, none
  with 20+. Pincode history on this file is noise. State rates are
  stable (Bihar 52.3%, UP 48.1%, MP 38.3% on Apr–Aug training data vs
  Maharashtra 17.6%), so states carry the geography signal. Pincode
  rules should wait until a pincode accumulates real history.

- **First-time buyers are never auto-cancelled (fake names excepted).**
  Considered: letting high scores cancel first-timers too. Rejected:
  first-timers are 75% of orders and cost Rs 300+ each to acquire.
  Cancelling them to save a Rs 169.40 return destroys the customer.
  The cap costs little — genuine first-timers with clean signals score
  low anyway — and it keeps the Marketing concern structurally
  protected instead of relying on threshold tuning.

- **Short-address and no-digit points do not stack.**
  Considered: adding both. Rejected after checking overlap: all 187
  short addresses in the file already lack a digit, so stacking would
  double-count a single signal. The engine takes the larger of the two.

- **Discount as 5% capped at Rs 40, not flat and not uncapped.**
  Considered: a flat Rs 30, and an uncapped 5%. Flat Rs 30 under-rewards
  larger orders; uncapped 5% loses money on high-value orders (Rs 150 on
  a Rs 2,999 order vs ~Rs 41.33 expected RTO saving per converted
  order). 5% capped at Rs 40 stays under the saving on every order
  value while scaling with basket size. The discount is only paid when
  the customer actually converts, so the per-converted-order comparison
  is the right frame.

- **Hinglish messages, and Hinglish is never a risk signal.**
  Considered: English-only messages, and scoring Hinglish addresses as
  risky. Rejected both: customers write addresses in Hinglish
  ("Station chowk se left, Hanuman Mandir ke saamne"), so confirmation
  in their own register is most likely to be answered; and Hinglish
  addresses returned at 30.8% RTO, close to the 28.4% average — penalising
  them would punish normal customers. Only missing structure (short, no
  number, fake name) is scored.

- **No rupee saving claimed for the confirmation bucket.**
  Considered: assuming a reply rate and an RTO reduction for confirmed
  orders. Rejected: the file cannot show who would reply, so any number
  would be invented. The memo reports the bucket's size and actual RTO
  rate and states the saving becomes measurable once reply rates are
  logged. The same honesty rule applies to the prepaid RTO rate (4%):
  it is brief-given, because the file contains only COD orders.

- **Conservative default thresholds (25/45/70), with the sweep shown.**
  A threshold sweep (see analysis notes) showed lower thresholds push
  the Ship-as-is RTO rate from 21.7% down to ~16% on September, but at
  the cost of WhatsApp-confirming 35–49% of all orders — delaying nearly
  half of shipments. The shipped defaults confirm ~20% of September
  orders instead. Recommendation: start conservative, measure reply
  rates and replied-vs-unreplied RTO for two weeks, then tune
  thresholds from measured data rather than from this file.

- **utm_source is not scored.**
  Considered: adding points for Meta-ads first-timers (34.3% RTO, the
  riskiest large segment). Rejected for the engine: utm is an
  acquisition-channel proxy, not an order property, and it is confounded
  with first-timer status. Penalising it inside the engine would quietly
  punish the channel bringing in most new customers. It is flagged in
  the memo as a monitored segment and a proposed experiment instead
  (confirm Meta first-timers in high-risk states first).

- **Static dashboard HTML, not a hosted app.**
  Considered: a Flask/FastAPI dashboard. Rejected: the brief asks for
  one screen the founder looks at each morning. A self-contained HTML
  file generated by one command has no server to keep alive, no login
  to manage, and runs anywhere — and the generator script
  (`dashboard.py`) is the part that would later be wired to live data.

- **Standard library only, no dependencies.**
  Considered: pandas for analysis. The shipped code uses only the
  standard library so the README's "under 10 minutes" claim holds on any
  machine with Python 3.10+, with nothing to install and nothing to
  break.

- **No live LLM wired in; a documented hook instead.**
  Considered: calling a language model at decision time for address
  judgement. Rejected for this submission: there is no model key in
  this environment, and claiming a live integration that does not exist
  would be dishonest. The deterministic checker covers every fake-name
  and address pattern actually observed in the file, and
  `llm_address_check` documents exactly what a model would be asked,
  what it would return, and why its answers must be logged and audited
  before they can cancel real orders.
